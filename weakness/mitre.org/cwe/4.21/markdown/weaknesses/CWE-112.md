# CWE-112: Missing XML Validation

## Description

The product accepts XML from an untrusted source but does not validate the XML against the proper schema.

## Detection Methods

- **Method:** Automated Static Analysis · **ID:** DM-14

  Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

  **Effectiveness:** High

## Potential Mitigations

- **Phase:** Architecture and Design · **Strategy:** Input Validation

  Always validate XML input against a known XML Schema or DTD.

  It is not possible for an XML parser to validate all aspects of a document's content because a parser cannot understand the complete semantics of the data. However, a parser can do a complete and thorough job of checking the document's structure and therefore guarantee to the code that processes the document that the content is well-formed.

## Demonstrative Examples

### Example 1

The following code loads and parses an XML file.

*Example (Bad, Java):*

```java
// Read DOM
try {
    ...
    DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
    factory.setValidating( false );
    ....
    c_dom = factory.newDocumentBuilder().parse( xmlFile );
} catch(Exception ex) {
    ...
}
```

The XML file is loaded without validating it against a known XML Schema or DTD.

### Example 2

The following code creates a DocumentBuilder object to be used in building an XML document.

*Example (Bad, Java):*

```java
DocumentBuilderFactory builderFactory = DocumentBuilderFactory.newInstance();
builderFactory.setNamespaceAware(true);
DocumentBuilder builder = builderFactory.newDocumentBuilder();
```

The DocumentBuilder object does not validate an XML document against a schema, making it possible to create an invalid XML document.

### Example 3

The following PHP code receives XML content from an HTTP request body, loads the XML content into a PHP SimpleXMLElement Object ($xml), and prints the results back to the user.

*Example (Bad, PHP):*

```php
$xmlContent = file_get_contents('php://input');
if (empty($xmlContent)) {
    http_response_code(400);
    exit('No XML content received.');
}
$xml = simplexml_load_string($xmlContent, 'SimpleXMLElement');
echo $xml->asXML();
```

The above PHP code is vulnerable because it directly loads XML from user-controlled input. It might assume that the XML is already compliant with the schema. According to PHP documentation, simplexml_load_string() only assumes a "well-formed XML string" [REF-1551]. So, the code does not actually validate its structure against a schema (XSD) or a Document Type Definition (DTD).

If the XML does not comply with the expected schema, this lack of validation could result in the application processing and handling malformed or unexpected data.

A separate validation step can ensure that any provided data is valid with respect to the expected XSD/DTD, to address CWE-112.

*Example (Good, PHP):*

```php
$xmlContent = file_get_contents('php://input');
// We skip a check that $xmlContent is empty
// Disable external entity loading to prevent XXE
libxml_disable_entity_loader(true);
libxml_use_internal_errors(true);
$dom = new DOMDocument();
$dom->loadXML($xmlString, LIBXML_NONET);
if (!$dom->schemaValidate('/xml/schema.xsd')) {
    http_response_code(400);
    exit('Invalid XML file.');
}
echo $dom->saveXML();
```

Note that the validation step in this code could be inefficient if it is only applied to inherently trusted files, but there are some scenarios in which an application must accept externally-submitted XML. In such cases, the schema validation could occur at an earlier step.
