# CWE-530: Exposure of Backup File to an Unauthorized Control Sphere

## Description

A backup file is stored in a directory or archive that is made accessible to unauthorized actors.

## Background Details

Often, backup files are renamed with an extension such as .~bk or .BAK to distinguish them from production files.

## Modes Of Introduction

- **Operation**: OMISSION: This weakness is caused by missing a security tactic during the architecture and design phase.

- **Implementation**:

  This renaming may have been performed automatically by the web server, or manually by the administrator.

  (All Phases: Implementation, Operation)

## Common Consequences

| Scope | Impact | Note |
| --- | --- | --- |
| Confidentiality | Read Application Data | At a minimum, an attacker who retrieves this file would have all the information contained in it, whether that be database calls, the format of parameters accepted by the application, or simply information regarding the architectural structure of your site. The source code for old files that were renamed in this manner and left in the webroot can often be retrieved. |

## Detection Methods

- **Method:** Automated Static Analysis · **ID:** DM-14

  Automated static analysis, commonly referred to as Static Application Security Testing (SAST), can find some instances of this weakness by analyzing source code (or binary/compiled code) without having to execute it. Typically, this is done by building a model of data flow and control flow, then searching for potentially-vulnerable patterns that connect "sources" (origins of input) with "sinks" (destinations where the data interacts with external components, a lower layer such as the OS, etc.)

  **Effectiveness:** High

## Potential Mitigations

- **Phase:** Policy

  Recommendations include implementing a security policy within your organization that prohibits backing up web application source code in the webroot.
