# CWE-707: Improper Neutralization

## Description

The product does not ensure or incorrectly ensures that structured messages or data are well-formed and that certain security properties are met before being used when received from an upstream component, or before being sent to a downstream component.

- **Primary**

## Modes Of Introduction

- **Implementation**: This weakness typically applies in cases where the product prepares a control message that another process must act on, such as a command or query, and malicious input that was intended as data, can enter the control plane instead. However, this weakness also applies to more general cases where there are not always control implications.
- **Implementation**: REALIZATION: This weakness is caused during implementation of an architectural security tactic.

## Notes

- **Terminology**:

  Neutralization is an abstract term for any technique that ensures that input (and output) conforms with expectations and is "safe." This can be done by:

  - checking that the input/output is already "safe" (e.g. validation)
  - transformation of the input/output to be "safe" using techniques such as filtering, encoding/decoding, escaping/unescaping, quoting/unquoting, or canonicalization
  - preventing the input/output from being directly provided by an attacker (e.g. "indirect selection" that maps externally-provided values to internally-controlled values)
  - preventing the input/output from being processed at all

- **Maintenance**: Concepts such as validation, data transformation, and neutralization are being refined, so relationships between CWE-20 and other entries such as CWE-707 may change in future versions, along with an update to the Vulnerability Theory document.

- **Theoretical**:

  This entry has the following dimensions:

  - Behavior-Type: "Neutralization"
  - Behavior-Property: "Improper"
